# P138《我是大廚》專案開發規範

**英文名稱：** I'm the Chef  
**文件代號：** P138-DS  
**規範版本：** v1.0  
**建立日期：** 2026-10-26  
**適用程式基準：** P138 V0.006（第三關 V0.007 為規劃階段）  
**上位規範：** SBI-P-SDS v3.4（2026-10-20）  
**單位：** 慈濟大學 經營管理學系 好玩實驗室

> **核心原則：共用廚房、物品先備、操作有因果、評分可解釋、逐關擴充。**

## 1. 目的與適用範圍

P138 是以 2D 網頁為介面的互動烹飪模擬遊戲。玩家從櫥櫃選取物品，完成備料、選鍋、加熱、調味、烹調與盛盤；系統根據行為、順序、用量、溫度與時間等狀態，判斷料理品質。各種數值均屬**遊戲模擬參數**，不等同經實測校準的烹飪或食品安全標準。

本規範約束後續所有 P138 的程式、UI、食譜、音效、測試、文件與 ZIP 交付。若與 SBI-P-SDS v3.4 抵觸，以上位規範為準。修改規範應升版並記錄原因。

## 2. 專案架構與技術

1. **前端優先：** HTML、CSS、原生 JavaScript、SVG；部署在 GitHub Pages。非必要不引入框架、npm、建置流程、外部 CDN。
2. **目前不使用資料庫：** 不要求登入，不儲存個人成績；遊戲狀態存在瀏覽器記憶體。`config-sample.js` 僅作交付範本；不得提交密鑰或正式部署用 `config.js`。
3. **模組化設計：** 將共享的物品定義、食譜規則、互動操作、模擬狀態、評分及視覺渲染邏輯分離；可逐步重構，不以增加新關卡為由複製整套廚房。
4. **未來啟用 Supabase 時：** 必須遵循 SBI-P-SDS v3.4 的 RLS Always On → No Direct Table Access → RPC Only → Least Data → Least Privilege；專案專屬命名空間、最小 GRANT、SECURITY INVOKER 預設、P130 帳號維護等要求。無資料庫階段不應增加無效的 API 呼叫。
5. **專案界線：** 不修改其他 P 專案的資料庫、資源、Auth 設定或 GitHub 儲存庫。

## 3. 固定畫面配置（自 V0.005 起）

桌面版優先採**單畫面、無上下捲動**的設計目標；仍須針對不同螢幕尺寸測試，窄螢幕可在必要時適度捲動，絕不可遮擋關鍵操作。

- **上排四櫥櫃（同一排）：** 食材櫃、調味料櫃、廚具櫃、碗盤櫃。點選櫃門展開物品；可設定一次只開一櫃。攪拌碗必須存放於「碗盤櫃」，不得以公告／提示區物件代替可拿取項目。
- **主工作區由左向右：** 備料區（相對較大）→ 瓦斯爐（緊鄰）→ 出菜區（相對較小）。
- **備料區：** 顯示所選物品；未來包含攪拌碗、洗菜槽與砧板等加工互動，但應盡量採同一工作區內切換工具／操作面板，不額外推高版面。
- **瓦斯爐：** 起始為空；先由廚具櫃取鍋並放上爐，才能進行需用鍋的加熱操作。火力旋鈕應緊貼瓦斯爐底部。
- **出菜區：** 起始為空；必須從碗盤櫃拿出餐盤，經備料區放入出菜區。放置後常駐，直至重新開始。未放餐盤不能盛盤或完成任務。
- **任務／狀態區：** 簡明顯示任務、步驟提示、操作回饋、溫度、油量、熟度及分數，不得擠壓主要互動空間。

## 4. 共用物品系統

### 4.1 物品類別

| 櫥櫃 | 示例 | 用途 |
|---|---|---|
| 食材 | 雞蛋、高麗菜、蒜頭、蔥、白飯 | 主食材、備料 |
| 調味料 | 沙拉油、鹽巴、醬油、糖、胡椒 | 用量與調味 |
| 廚具 | 平底鍋、炒鍋、鍋鏟、打蛋器、菜刀、砧板 | 加熱與加工 |
| 碗盤 | 攪拌碗、餐盤、其他容器 | 混合、盛盤 |

類別是介面分類，不代表每道料理都能使用所有物品。新物品至少需有唯一 `itemId`、顯示名稱、圖示／素材、櫥櫃分類、可放置區域、可執行動作、錯誤反應、鍵盤／觸控替代操作，以及必要的遊戲狀態。

### 4.2 取用與誤用

- **取出／查看**不等於**使用**：一般探索不扣分。
- 拖曳到合法區域並放開才執行用途；不合法的操作應提供原因及回復手段。
- 關卡規則可區分 `required`、`optional`、`forbidden`（針對本關指定食譜，而非宣稱其他真實食譜都錯誤）。
- 誤將不適用物品加入料理可扣分，須寫入失誤紀錄並於結算說明；**不能僅因拿錯或放回而扣分**。
- 明顯危險的操作應阻止並提示，不將不安全行為做成可模仿的操作教程。
- 誤用扣分與硬性失敗必須由食譜設定明定，避免不同關卡行為不一致。

### 4.3 備料（Mise en place）

玩家從櫥櫃選取必需物品並放到備料區，作為關卡起始階段；應可看見已準備清單、缺少物品及各物件所在位置。每個必要食材與工具都必須在櫥櫃中找得到且可完成對應操作。禁止出現「任務需要某物品，但無法取得」的死局。

## 5. 烹飪模擬與互動規格

1. **輸入方式：** 滑鼠拖曳、Pointer Events 觸控操作、必要時鍵盤替代；物件移動應有放置目標提示及命中回饋。
2. **倒油／液體：** 使用持續時間、視需要加入傾斜角度決定用量；需定義流速、下限、上限、流入容器與溢出結果。遊戲倍率不應無意造成按住相同真實時間卻倒出不同油量。
3. **火候／鍋溫：** 火力設定不使溫度瞬間跳變；以明示的離散時間步長更新鍋溫，考量鍋具與食材狀態的簡化熱變化。未放鍋不可加熱料理。
4. **攪拌：** 依持續操作或移動軌跡增加混合度；不可只播放動畫卻不改變狀態。
5. **翻炒：** 依拖動鍋鏟的移動區域與間隔影響受熱均勻性、熟度與焦化；勿用單一點擊等同完整翻炒。
6. **盛盤：** 必須有餐盤在出菜區，且食物完成必要烹調後，才可從鍋中盛出與結算。
7. **關卡重置：** 恢復所有物件位置、鍋具、餐盤、計時器、溫度、油量、熟度、音效狀態以外的遊戲狀態及扣分紀錄。跨關卡不殘留前關烹飪狀態。
8. **狀態顯示：** 主要數值需有合理單位，狀態改變須可視化並提供操作回饋；內部模擬數值不偽裝為測量儀器讀值。

## 6. 食譜資料與關卡擴充

每道菜應以資料驅動規則為主，逐步將食譜獨立存成 JSON；原有程式可循序遷移，不能因格式改造破壞既有關卡。食譜的最低設計欄位：

```json
{
  "recipeId": "P138-R003",
  "nameZh": "清炒高麗菜",
  "nameEn": "Stir-fried Cabbage",
  "status": "planned",
  "requiredItems": ["cabbage", "garlic", "oil", "salt", "wok", "spatula", "knife", "board", "plate"],
  "optionalItems": [],
  "preparationActions": ["wash_cabbage", "cut_cabbage", "prepare_garlic"],
  "cookingActions": ["place_wok", "add_oil", "heat", "add_garlic", "add_cabbage", "stir", "season", "plate"],
  "simulationPolicy": "prototype-1",
  "scoringPolicy": "P138-R003-draft-1"
}
```

*以上為規範格式示例，不代表 V0.006 已實作 JSON 引擎或第三關。* 每道食譜可定義步驟前置條件、順序限制、容許量、時間、溫度、熟度、誤用與硬性失敗條件。可供探索的自由料理模式屬未來功能，不得與教學挑戰模式評分混用。

## 7. 關卡狀態與規劃

| 關卡 | 名稱 | 主要機制 | 狀態 |
|---|---|---|---|
| 001 | 荷包蛋 / Fried Egg | 選鍋、倒油、開火、下蛋、熟度、先備餐盤再盛盤 | 已納入 V0.006 |
| 002 | 香嫩炒蛋 / Scrambled Eggs | 兩顆雞蛋、攪拌碗、打蛋器、倒蛋液、翻炒、出菜 | 已納入 V0.006 |
| 003 | 清炒高麗菜 / Stir-fried Cabbage | 洗菜、切菜、蒜頭處理、炒鍋、鹽量、翻炒與水分 | **規劃中（目標 V0.007）** |

### 7.1 第三關既定設計方向

- 採 **B：實際操作備料**；洗菜以滑鼠／觸控移動軌跡衡量覆蓋率，切菜以刀具跨越切割線判定。
- 高麗菜與蒜頭需前處理；炒鍋放上爐後加油、加熱、先放蒜頭再下高麗菜，使用鍋鏟翻炒、加鹽並盛盤。
- 模型記錄沖洗覆蓋率、切割完成與均勻度、油量、鹽量、鍋溫、翻炒覆蓋、熟度、水分與焦化程度。
- **建議評分 100 分：** 選物 10、洗菜 10、切菜與蒜頭處理 15、油與調味 15、火候與順序 20、翻炒與熟度 20、出菜 10。這是待開發的設計權重，並非已驗證的演算法。
- 建立食譜可調參數；例如約 200 g 高麗菜時的 5–12 mL 油、0.4–1.2 g 鹽，目前只作為先前討論的**遊戲原型測試假設**，不得列為真實烹飪標準或安全保證。
- 洗菜模擬覆蓋率不得宣稱代表食品衛生合格；對玩家提示使用流動清水清洗，不採用洗潔精清洗蔬菜的玩法。

## 8. 評分、通關與可解釋性

- 全關卡以 100 分為基準，分數項目及權重由每道食譜定義。
- **軟性扣分：** 份量略偏差、操作不均、誤用非指定調味料等。顯示扣分原因、行為與建議改善方式。
- **硬性通關條件：** 必須使用主食材、完成必要前處理／加熱與盛盤；未準備餐盤不許出菜。嚴重危險或不可能完成狀態應阻止並提示。
- 評分須依實際記錄的操作事件與模擬狀態計算，不得只檢查是否點擊過每個按鈕。對不同食譜的特殊手法採設定化判斷，不將單一烹調路徑宣稱普世正確。
- 交付前以正常、邊界、失敗三類情境測試；應能重現相同操作得到一致評分。

## 9. 音樂、視覺與無障礙

- 維持溫馨、可愛、易辨識的 2D 卡通風格；icon、物品顏色及命名全站一致。
- 背景音樂與料理音效分開開關；音量可調。V0.006 沿用 Web Audio API 合成音樂；使用者互動後才啟動播放，不強迫自動有聲播放。
- 物品可辨識名稱與圖示，不僅靠顏色區分；按鈕提供鍵盤焦點及明確文案；觸控目標保持可操作。
- 大小螢幕均避免物件重疊、拖曳區域錯位、出菜區被遮蓋或重要步驟需要過度捲動。
- 若未來導入外部音樂、圖片或字型，須保留來源與授權資料；不得提交未授權素材。

## 10. 版本規則、交付與部署

- **Web Version** 採 `V0.001`、`V0.002`…遞增；每次修改玩家可見或可操作功能就升版。
- `index.html` 顯示版本，CSS／JS query-string cache busting、README 首段、規格記錄、ZIP 檔名需同步；不得只改其中一部分。
- 正式 ZIP 檔名建議 `P138_ImTheChef_V0.007.zip`，內部**唯一同名根資料夾** `P138_ImTheChef/`。
- 至少包含 `index.html`、`styles.css`、`app.js`、`README.md`、`config-sample.js`、`assets/`、`database/`、`docs/`；純前端階段 `database/` 明確標示 no-op，不做任何無關 SQL 操作。
- 不放入正式 `config.js`、密碼、private keys、service_role 或個資。
- GitHub 部署前先盤點既有 `main`，保存未修改檔案，檢查版本差異，提交單一可追蹤 Commit；**只有實際提交且檢查 Pages 網站後，才能宣稱已部署**。
- 依 SBI-P-SDS v3.4，展示型專案視需要提供 A3 直式海報（PDF + SVG），QR Code 只能以真實網站 URL 產生，不可由生成圖片代替可掃描 QR Code。

## 11. 交付前檢查清單

- [ ] 三個既有／預定關卡的狀態清楚標註；新關不破壞荷包蛋、炒蛋。
- [ ] 食譜中所有 `requiredItems` 都有合法櫥櫃入口，取物、備料、使用動作完整可達。
- [ ] 四櫥櫃排於頂部；左備料、中瓦斯爐、右出菜；火力緊貼爐子。
- [ ] 未放鍋不能執行需鍋加熱；未放餐盤不能盛盤；重置後兩者回復初始狀態。
- [ ] 誤取物品不扣分，誤用才按關卡規則計分；錯誤提示可理解。

- [ ] 滑鼠、觸控、鍵盤的主要操作能完成；桌面版盡量不需上下捲動。
- [ ] 背景音樂／音效各自可關閉，無未授權外部音源。
- [ ] HTML／CSS／JavaScript 語法與資源路徑檢查通過；實際完成正常與失敗流程測試。
- [ ] ZIP 結構、README、版號、CSS／JS cache busting、文件一致。
- [ ] 執行 SBI-P-SDS v3.4 QA-01 至 QA-15：無資料庫條款註明 N/A；需真人審查者標 REVIEW，不假稱全部 PASS。
